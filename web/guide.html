SENTINEL: the team's end-to-end explanation

Edition: 21 October 2026. Audience: every hackathon teammate, presenter and reviewer. This guide describes the implemented pilot, explains its reasoning in plain language, and separates measured evidence from demonstrations and future plans.

Read the tutorial for a live demonstration, operations for setup and alerts, and reference for exact API details.

1. The project in one minute

SENTINEL helps teams decide where to investigate connectivity, plan affordable verification visits, and track problems at individual facilities. The hackathon supplied an Ookla dataset. We added administrative boundaries and health/education facility records, built spatial processing, designed interpretable screening rules, and created two interfaces: an initial Streamlit planner and a dedicated web application.

The latest implementation adds a facility register, persistent observation history, incident ownership and recovery, notification previews, email/SMS adapters and an optional synthetic-upload probe. Demonstration tests are always labelled DEMO and never sent externally. Field observations require a configured token. No real provider delivery has been performed during development.

Our creativity is the complete decision workflow: evidence → uncertainty → prioritized visits → facility inspection → measurement → incident → action → recovery. Merely combining more datasets would not establish that workflow.

2. The problem we can actually answer

Historical speed measurements can help identify places needing investigation. They cannot establish that a particular polling unit can transmit a result today. Facilities identify socially useful locations to assess, but their existence does not prove network demand, operating status or current service.

Our first question is: “Where should a team spend its limited verification budget?” Our second is: “Once a site is monitored, can we detect repeated upload problems and record a response?” The answers support planning and accountability. They do not certify electoral readiness, prove misconduct, predict election outcomes or replace an authorized election system.

3. The vocabulary everyone needs

• Geospatial data: information tied to locations on Earth.

• Coordinate: latitude and longitude describing a location. Longitude is east/west; latitude is north/south.

• Point: one location, such as a clinic. Polygon: an outline enclosing an area, such as an LGA. Raster: a grid of pixels, such as a satellite image.

• Tile: a geographic cell summarizing measurements. It is not a mobile tower or a verified place to upload.

• LGA: local government area. A stable identifier distinguishes areas that may share a name.

• Spatial join: assigning a point to the area that contains or intersects it. Imagine putting every clinic pin into its correct LGA folder.

• CRS: coordinate reference system. EPSG:4326 describes longitude/latitude in degrees; degrees are not kilometres.

• GeoPackage: a file that stores spatial tables. GeoJSON: a geographic JSON format. CSV: a spreadsheet-like text table.

• API: a structured way for software to request data or submit a record.

• Provenance: where a record came from and how it was processed.

• Idempotency: repeating the same report with the same identifier does not count it twice.

• Outbox: a persistent queue of messages waiting for delivery.

4. What data we used

Ookla was the provided dataset. The following counts describe the local extracts, not the total number of facilities or network observations in Nigeria.

• Ookla: 9,234 rows; 9,209 matched to an LGA, 25 unmatched. Upload, latency and test count feed the screening. Observation dates and fixed/mobile provenance have not been verified in the local extract.

• LGA boundaries: 774 areas used to organize the evidence. Shared-boundary cases are assigned deterministically by stable ID so one observation is not counted twice.

• GRID3 health: 41,778 source records, with 35,774 non-empty geometries. Of those, 35,772 matched the baseline LGA count. The 6,004 excluded records remain in the source file; we did not invent locations for them. Not every record is a primary health centre.

• HOT OSM education: 6,329 source records; 6,327 matched the baseline LGA count. This is not the separate GRID3 education dataset mentioned in the original guide, nor a complete national school census.

• HOT OSM health: 7,736 records, now included in the facility register. It supplements inspection and reconciliation; it is not added to GRID3 totals as if every record were a distinct clinic.

The register has 49,839 source records with non-empty geometry. It flags 914 potential GRID3/HOT health duplicates using exact normalized names within approximately 200 metres. It does not automatically merge them. A missing duplicate flag does not establish uniqueness.

The supplied OpenCellID resource is useful for future cellular context but is not connected in this build. Cell observations are not a complete tower inventory or live tower-status feed. The supplied nighttime-light version covers 1992–2020 at approximately 1 km resolution; it is not current power monitoring and has not been integrated. Meta relative wealth and population assets elsewhere in the folder are not used by the current scoring pipeline. Do not list them as implemented analytical inputs in the presentation.

5. How raw data becomes the evidence map

The evidence builder reads LGA polygons and standardizes their CRS. It reads Ookla upload, latency, tile coordinates and test counts. Upload values are converted from kilobits per second to megabits per second by dividing by 1,000.

Each tile coordinate becomes a point. A spatial join assigns it to an LGA. Where a point intersects two boundary polygons, stable-ID ordering chooses one assignment. We then group by LGA identifier and calculate observed tile count, mean upload, mean latency and total tests.

The averages are unweighted means of tile averages. A tile with many tests does not receive extra weight in the current mean. This is a transparent pilot choice, but it does not represent population-weighted experience or remove measurement selection bias.

Health and education geometries are converted to representative points where needed and assigned to LGAs. Representative points lie within the geometry; they are not validated entrances or GPS measurements. Missing observation metrics stay unknown. Facility counts are zero only when the available source contributes no matched records, not proof that no facilities exist.

The builder also finds proximity to a historical tile with upload at least 2.5 Mbps and latency below 80 ms. It converts coordinates to a three-dimensional unit sphere, finds the nearest point with a spatial search tree, then converts the chord to great-circle kilometres. The origin is an interior representative point of the LGA. This is neither road distance nor distance from every facility. The historical tile is not a verified accessible upload station.

Outputs are sentinel_evidence.csv, sentinel_evidence.geojson and sentinel_sources.json. Both interfaces read these outputs rather than repeating expensive spatial joins on every click.

6. The screening formula, with an example

We use two bounded deficits. “Bounded” means values are limited to the range zero to one.

Upload deficit = clamp((2.5 − mean upload Mbps) / 2.5, 0, 1).

Latency deficit = clamp((mean latency milliseconds − 50) / 200, 0, 1).

Screening score = 100 × (0.70 × upload deficit + 0.30 × latency deficit).

Example: an LGA with 1 Mbps upload and 150 ms latency has upload deficit 0.6 and latency deficit 0.5. Score = 100 × (0.70 × 0.6 + 0.30 × 0.5) = 57. This falls in “Review performance.” It does not mean a 57% probability of upload failure.

Categories: below 35 is lower observed concern; 35 to below 65 is review performance; 65 or higher is poor observed performance. An LGA without usable measurements remains unscored and grey. The current output contains 234 LGAs with no observed tiles.

“Larger sample” requires at least ten observed tiles and thirty tests. It does not establish statistical representativeness or freshness. Unknown areas receive verification priority 75 so they can receive field attention; 75 is an allocation policy, not an invented risk measurement.

The original blueprint proposed four weighted factors and a “feasibility” index where high values meant failure. We implemented a simpler, explicitly named screening score based on fields available in the actual extract. We did not implement alleged BVAS TCP-timeout thresholds, blackout fractions from absent tests, invented roaming benefits or fixed percentages of protected voters.

7. How the visit planner works

Users choose available budget, cost per visit and team capacity. The planner ranks LGAs by verification priority, breaks ties by stable ID and selects the highest priorities within all limits.

Visit count = minimum(eligible LGAs, team capacity, whole visits affordable from budget).

Example: a ₦500,000 budget, ₦100,000 per visit and capacity of three produces three visits, ₦300,000 estimated spend and ₦200,000 remaining. Equal visit cost makes ranking straightforward. If costs differ by area, a different optimization model is needed.

The shortlist proposes initial LGA verification visits. It does not allocate satellite terminals, select fibre routes or quantify social return on investment. Schools and clinics give context for the next investigation; they do not silently alter the current score.

8. Why we have two interfaces

Streamlit let us validate analytical logic quickly using Python. It includes filtering, a map, an evidence table, budget controls, downloadable scenarios and briefs, and session-based rehearsal notes. Its theme was corrected after contrast problems made the interface difficult to use.

The dedicated web app separates the browser interface from the Python service. It adds linked map/queue selection, pan and zoom, map colour layers, an inspector, browser-persistent bookmarks, plan comparisons, CSV downloads and printable briefs. It serves custom HTML, CSS and JavaScript, not a Streamlit page in a wrapper.

Both use readiness.py. Both now expose the facility register and persistent monitoring workflow. The original Streamlit rehearsal notes remain session-only; its new monitoring tab shares SQLite records with the web app. Web bookmarks and plan comparisons remain in that browser, not in shared team accounts.

9. What the new monitoring system does

The facility register provides source-based identity and context. Each facility also has a nearest historical Ookla tile, its straight-line distance, upload and latency. A nearby observation is context only: it is not a test at the facility, and its date and network type remain unverified. A report says which site was tested, when, whether the upload completed, how long it took, and the reporting mode. The server separately records receipt time.

DEMO reports are synthetic exercises. FIELD reports arrive through a token-protected API, either from the authorized reporting form or the optional probe; the label means submitted field evidence, not independent verification. A shared token cannot establish who physically stood at the site. Device enrollment, per-device credentials and identity validation are future deployment work.

Reports are saved in SQLite, a local database suitable for this pilot. Repeating an identical event ID does not add another report. Reusing an ID with different contents is rejected. Late reports remain available as history without changing the current incident state. Demo and field events never combine to satisfy a failure streak.

Three recent consecutive failures open an incident. Two recent consecutive successes record recovery. An officer can acknowledge an incident and record an action; this preserves a separate audit entry. Acknowledgment and recovery are different facts.

The system creates SMS and email entries when an incident opens and recovers. A separate worker handles sending and one escalation for a field incident left unacknowledged for fifteen minutes. Preview mode is the default. Even with sending enabled, demo entries never leave the application.

10. How actual measurements and alerts can travel

The optional probe runs on an authorized device. It uploads 64 KiB of synthetic bytes to SENTINEL's own endpoint. The server counts and discards them. The probe measures elapsed time, then submits a small report. It stores pending reports locally and retries them after connectivity returns. Use one process per queue file.

This measures the device-to-SENTINEL path. It does not test INEC's servers or authenticate a BVAS device. Power loss, endpoint errors, credentials and device faults can also produce failures. A complete outage prevents immediate reporting over the failed connection. The UI therefore calls old field reports stale; it does not claim that a missing report proves an outage.

The web monitoring page polls every fifteen seconds. The optional probe waits five minutes after each test cycle, and the worker checks every fifteen seconds. These are schedules, not a guaranteed end-to-end service level. Delay also includes network outages, retries, provider queues and recipient availability.

SMTP sends email using an encrypted STARTTLS session. The Twilio adapter submits SMS through its Messages API. Credentials and recipient destinations live in server-side environment variables. A provider-accepted status does not prove delivery or that a human has read or acted on a message. Ambiguous failures require provider reconciliation before retrying to avoid duplicate sends.

11. What stakeholders can reasonably take away

For an electoral operations team, the system can organize verification work around actual authorized sites once an authoritative polling-unit register is supplied. It does not provide official results transmission.

For health administrators, the facility register provides a starting point for choosing clinics to assess and monitor. For education teams, it does the same for educational records. For infrastructure planners, clusters can motivate investigation into shared demand, but commercial viability still needs operating status, costs, bandwidth demand and partner commitments.

ODK, DHIS2 and agency-dashboard integrations remain proposed. We have implemented the API boundary that can support adapters; we have not connected to those institutions. We also have not proved backhaul congestion from tower proximity, power availability from darkness, or causation from wealth/connectivity correlations.

12. What is finished and what remains

Implemented locally: evidence preparation, transparent scoring, constrained visit planning, both interfaces, searchable facility register, conservative duplicate flags, persistent observation/incident/audit/outbox storage, incident rehearsal and recovery, field ingestion token, synthetic probe with retry queue, SMTP/SMS adapters, worker escalation, source audit and this guide.

Requires configuration and partner testing: provider accounts, permitted sender and recipient, secure hosting, authorized site devices, current measurements, costs and calibrated alert thresholds. No live SMS/email has been sent or delivery verified in this development session.

Future engineering: PostgreSQL/PostGIS migration for distributed use, per-user/device authentication, access-controlled read APIs, rate limiting, recipient routing, verified delivery receipts, automatic heartbeat alerts, source-download scheduling, identity reconciliation across source releases, external integrations, backups/restore rehearsal and load testing. Docker packaging exists but has not been built or deployed here.

13. Questions judges may ask

“Why not treat untested areas as disconnected?” Because absence of observations does not establish absence of service. We prioritize verification instead.

“How did you know where the clinics belong?” We matched their coordinates to LGA polygons with a spatial join, recording unmatched rows separately.

“Are these all polling units?” No. These are facility datasets. Official polling-unit linkage requires authoritative records.

“Why are the health counts different?” Source rows, usable locations and matched locations are different totals. We expose that distinction and retain the audit.

“Is the system real-time?” The historical baseline is static. The new monitoring pipeline can accept repeated reports and refresh the interface. Its usefulness depends on deployed probes, recent observations and a working network.

“What did the team add beyond Ookla?” Administrative organization, facility context, uncertainty handling, a reproducible pipeline, actionable budget planning, a reusable API, interactive interfaces and an incident-response workflow.

“Can it scale nationally?” The separation of components supports evolution, but the current local SQLite pilot has not been nationally load-tested or secured for public deployment.

Demonstrate SENTINEL in ten minutes

This walkthrough is for any teammate, including someone with no GIS or programming background. Ask the maintainer to start both applications first. You need a browser; no geospatial software is required.

First result in three steps

1. Open http://localhost:8600/. The national map and evidence totals appear.

2. Type an LGA name in the search box or select one on the map. Its evidence appears in the inspector.

3. Change the visit budget. The proposed visits and estimated spending update. You have turned data into a resource-constrained action plan.

Say: “The colours summarize historical observations. Grey means insufficient evidence. Our next action is to verify conditions at real sites.”

Explore and explain

Reset filters to restore the full country. Compare the observed-performance layer with the evidence-sample layer. A larger sample is more observations, not proof that the data is current. Bookmark two areas, enable bookmarked-only planning, and change team capacity. The shortlist must respect the budget and capacity; it does not estimate voters protected or new network coverage.

Save a comparison, alter the budget, and explain the difference. Download the shortlist CSV. Export the HTML briefing, open it, and use the browser's Print command to save a PDF. The report includes assumptions and limitations.

Rehearse an incident

Open “Facilities & alerts.” Search a familiar clinic or school name, or select a record from the first page. Read its source, location, type and duplicate warning. These are source records, not verified polling units or confirmed operational facilities.

Click “Record failed demo test” three times, allowing each request to finish. An incident opens and two notification previews appear: one SMS and one email. Both say DEMO. No messages leave the system.

Enter an officer name and a concrete action such as “Check power and repeat on another carrier,” then acknowledge. The incident now has an owner and action note. This does not mean connectivity has recovered.

Click “Record successful demo test” twice. The incident resolves and recovery previews appear. Explain that the rule is illustrative. We demonstrate an evidence-to-action workflow, not actual failures at that facility.

Refresh the page. Records persist in the local database. The page also refreshes automatically every 15 seconds when visible, except while you are typing an incident response.

Show the Streamlit version

Open the address printed by Start SENTINEL.cmd (normally http://localhost:8502/ on this machine; check the launcher). The sidebar filters the map and visit plan. Use the numbered tabs: evidence, budget/briefing, and the original demo observation.

The original “Demo observation” tab saves session notes and gives a suggested next step. Those notes are separate from persistent monitoring. Open “Facilities & alerts” to search facilities in the selected LGA, record persistent demo tests, acknowledge incidents and inspect previews. The web and Streamlit operations screens share the database.

Say: “Streamlit helped us validate the analysis quickly. The dedicated web app gives us a more interactive workflow. Both use the same scoring functions, so we do not maintain competing formulas.”

Three-minute judge demonstration

• 0:00–0:30: Introduce the provided Ookla data and the decision problem: where should teams verify connectivity first?

• 0:30–1:00: Show the map, a grey LGA and a measured LGA. Explain unknown versus poor evidence.

• 1:00–1:30: Set a visit budget, bookmark locations and export a shortlist.

• 1:30–2:30: Open a facility, record three DEMO failures, acknowledge the incident, then record two successes.

• 2:30–3:00: Explain that SMTP/SMS adapters are ready for configuration, actual sends remain disabled, and a partner pilot would validate the rules and data freshness.

Do not claim that the demo proves a real network outage, election readiness or lives/voters protected. Do not say every health record is a primary health centre or every education record is a school polling unit.

Troubleshooting during a demo

• No facilities: ask the maintainer to run python -m src.facilities.

• No incident after three clicks: use the same facility; all three failures must be recent and consecutive. A success interrupts the streak.

• Incident remains acknowledged: two recent consecutive successful tests are required for recovery.

• Blank/failed requests: check that the server is running and reload. Do not substitute an old screenshot for current evidence without labelling it.

• No external message: expected in preview mode; show the outbox and explain the configuration boundary.

What you built: a reproducible demonstration that links historical evidence, resource planning, facility inspection and a traceable response workflow. For the full explanation see TEAM_GUIDE.md; for setup see OPERATIONS.md.

How to run, refresh and operate SENTINEL

Read the tutorial first for the user workflow. Reference lists all fields and environment settings. The team guide explains the data and claims.

How to start both interfaces

Use Python 3.11 and a terminal opened in the project folder. The downloaded source GeoPackages and boundary GeoJSON must be present for rebuilding. Existing prepared files are sufficient to run the apps.

python -m pip install -r requirements.txt
python -m uvicorn src.web_api:app --host 127.0.0.1 --port 8600

Open http://localhost:8600/ for the web app. Start SENTINEL Web.cmd is a double-click alternative. In a second terminal:

python -m streamlit run src/app.py --server.port 8502

Open http://localhost:8502/. The existing Start SENTINEL.cmd does not explicitly set a port, so its console may show 8501 or another available port. Use the printed address. The new operations tab links to the web server on 8600.

If the port is occupied, stop the existing instance in its terminal before starting a replacement. Do not terminate unrelated Python or notebook processes. Both apps must use the same database path to share monitoring history.

How to rebuild evidence and facilities

Preserve the original files and source attribution. Inspect a new release before replacing an extract. Especially check identifiers: feature IDs may change between releases, so a register refresh must not silently attach old observations to a different facility.

python src/spatial_engine.py
python -m src.facilities

The first command rebuilds LGA evidence and its audit. The second rebuilds the register and duplicate-candidate audit. Check data/sentinel_sources.json and data/facilities_audit.json. Restart FastAPI to refresh its historical evidence cache. The register itself is reloaded when its file timestamp changes.

These commands process local extracts. They do not download new remote source releases automatically. Review changed counts, unmatched locations, source licence and observation date before accepting an update. A download date is not the measurement date.

If a source file is missing, restore it at the path named in the error. If a source schema changes, update the builder deliberately and rerun the tests. Do not replace unknown measurements with zero speed.

How to rehearse without sending messages

Keep SENTINEL_SEND unset or 0. Open /monitor.html, choose a facility and record three failed demo tests. Acknowledge the incident and record two successful demo tests. All rows remain visibly DEMO. Review the SMS/email previews. The worker also refuses demo entries even if sending is enabled.

python -m src.delivery

Without send configuration, this returns a preview-only status and sends nothing. It can still queue an escalation for eligible field incidents. Tests use temporary databases and mocked providers, not real recipients.

How to configure authorized field reporting

Set a strong SENTINEL_INGEST_TOKEN in the API server environment and on each authorized probe. Do not put it in frontend JavaScript or a committed file. This version uses one shared token; individual-device enrollment is future work. The .env.example file documents names but is not automatically loaded.

For a manual report, open Facilities & alerts, select a facility, switch Reporting mode to Authorized field report, and enter the configured operator token, measured seconds, carrier and context. Submit the actual success/failure outcome. The form does not perform a network test and timestamps the report now; use the API for earlier observations. The same token enables field-incident acknowledgment. It is kept only in the current page, cleared when returning to demo mode, and never saved in browser storage.

For an automated probe, choose an actual registered site ID from the interface. Verify that the device is physically at the intended site and that the facility has agreed to the test. With the token already set securely in the process environment:

python -m src.probe --site GRID3:65 --carrier "Pilot carrier"

GRID3:65 is an example register ID, not a recommendation to deploy at that facility. Replace it with the agreed site. The command performs one 64 KiB synthetic upload to the default localhost server and queues/submits a field report. Localhost tests validate software only, not external connectivity.

For an authorized hosted pilot, supply --url https://your-approved-server and --watch. HTTPS is required except for localhost. The loop waits 300 seconds between cycles. Use --queue to give each probe its own writable queue file. Do not run two probes against one queue.

The queue survives temporary network failure. Reports retain original test times; old reports do not rewrite current incidents. If queued_reports grows, check connectivity, server availability, token and site ID. Do not discard reports to hide a failure. The queue stops collecting at 10,000 pending reports until the issue is resolved.

How to enable email or SMS delivery

First obtain an authorized destination and a configured provider account. For email, configure SMTP_HOST, SMTP_PORT, SMTP_FROM, SMTP_USER, SMTP_PASSWORD and SENTINEL_EMAIL_TO in the worker environment. The adapter uses STARTTLS and authentication; it does not support a plaintext relay or implicit-TLS port 465 in this version.

For SMS, configure TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_FROM and SENTINEL_SMS_TO. Verify sender availability, country permissions, destination format and account/trial restrictions with the provider. Actual delivery costs are provider-specific and are not part of the visit budget.

Only when the team has approved the destination and sending purpose, set SENTINEL_SEND=1 in the worker environment and run:

python -m src.delivery --watch

The worker processes up to 25 pending field messages per channel per cycle. It will also process old pending field notifications: inspect the outbox before enabling sends. The initial adapter uses one destination per channel; it does not automatically know which commissioner or LGA officer should receive a message.

Verification requires a controlled field-mode test, checking provider acceptance, actual recipient receipt, and operator acknowledgment separately. None of those external delivery checks has been performed here because provider credentials and approved recipients have not been configured.

How to handle delivery failures

If messages stay pending, confirm the worker is running, sending is enabled and every required variable for that channel is present. The worker and API may have different environment variables; the dashboard's delivery label reflects the API process, not proof that a worker is running.

If status is review_required, inspect the provider console without copying credentials into logs. A timeout can happen after acceptance; do not blindly retry. A crashed worker may leave sending. Reconcile that entry with provider history before a maintainer changes its status. The pilot intentionally has no one-click retry for ambiguous submissions.

Provider_accepted means the provider accepted a request. SMS delivery receipts and email bounce handling are not implemented. Operator acknowledgment is recorded in SENTINEL separately. A missed fifteen-minute acknowledgment queues one escalation to the same configured destinations.

How to protect and back up the pilot

Keep the server bound to localhost for demonstrations. Before shared/public hosting, add user authentication, read authorization, per-device credentials, rate limits, TLS termination, audit access policies and a retention policy. The current public read endpoints and unauthenticated demo controls are intended for a local pilot.

Stop the apps and worker before making a simple file copy of data/monitoring.sqlite3; retain source snapshots and prepared data alongside it. Restore-test a backup before relying on it. Do not store the database on an unreliable network share. A container needs a persistent data volume; otherwise recreating it can lose monitoring history. The supplied Dockerfile is packaging preparation, not a verified deployment.

How to verify changes

python -m unittest discover -s tests
python tests/check_app.py
node --check web/app.js
node --check web/monitor.js

Unit/API tests cover scoring, budgets, unknown semantics, endpoint validation, persistence rules and mocked delivery. Streamlit checks cover initial render, zero budget, session rehearsal and empty filters. Browser verification should cover facility selection, three failures, acknowledgment, two successes, retained history, empty search and readable layouts.

On this Windows environment, API tests may need an unrestricted local terminal because sandbox socket restrictions can block the test event loop. A hanging sandbox test does not itself prove an application defect.

How to regenerate the printable team guide

python -m src.build_guide

This combines the four Markdown documents into web/guide.html. Open /guide.html and print to PDF. The Markdown documents remain the editable source. Update both the guide and implemented-status notes whenever features change.

SENTINEL technical reference

Read the team explanation, the demo tutorial, and the operating guide for context and instructions.

Components and persistence

• src/spatial_engine.py: offline evidence builder. Uses the local Ookla GeoPackage, LGA boundaries, GRID3 health and HOT education. Writes CSV, GeoJSON and a source audit.

• src/readiness.py: shared scoring, equal-cost visit allocation and escaped HTML brief generation.

• src/facilities.py: offline facility register builder. Adds HOT health, source attributes, representative locations, LGA assignments, nearest historical Ookla context and possible cross-source duplicates.

• src/web_api.py: FastAPI routes and static web hosting. Historical evidence and boundary geometries are cached until restart; facility CSV cache refreshes when the file modification timestamp changes.

• src/app.py: Streamlit interface. Uses the same analytical logic and monitoring database. Evidence caches use file modification timestamps.

• src/monitoring.py: SQLite observation history, incident state, acknowledgment audit and notification outbox.

• src/delivery.py: explicit SMTP/Twilio worker. Default preview only. --watch repeats every 15 seconds. Sends only field-mode entries.

• src/probe.py: synthetic 64 KiB upload test, timestamped field report and local retry queue. --watch waits 300 seconds after each cycle. One process per queue file.

• web/index.html, app.js, style.css: evidence map and visit planner.

• web/monitor.html, monitor.js, monitor.css: facility search, demo controls, incidents, and notification previews. Polls every 15 seconds while visible and not editing an incident form.

• data/monitoring.sqlite3: persistent local pilot database. Override with SENTINEL_DB. SQLite serializes writes; this is not a distributed database deployment.

API routes

FastAPI's interactive schema at /docs is the complete machine-readable request reference.

• GET /api/health: status and LGA count; this is not a complete dependency health check.

• GET /api/evidence: all scored LGA rows. Unknown scores are JSON null.

• GET /api/boundaries: simplified LGA display geometry, tolerance 0.008 degrees. Analytical joins use original geometry.

• POST /api/plan: JSON budget (0–100 billion naira, default 5 million), cost_per_visit (1–1 billion, default 100,000), max_visits (0–774, default 20), optional ids (up to 774). Unknown IDs are rejected. Empty ids means empty scope.

• POST /api/brief: same input as plan; returns printable HTML with scenario assumptions.

• GET /api/facilities: q (literal name or site-ID substring, max 100 characters), source (exact source name), lga (shapeID), offset (nonnegative), limit (1–100, default 30). Returns total and items.

• GET /api/sources: generated source and facility audits.

• GET /api/monitoring: optional site_id filters observations and incidents. Returns latest 100 observations, incidents, notifications, and audit entries. Outbox and audit remain global. Includes server update time and delivery setting. This pilot read endpoint has no user authentication; keep it local until access controls are added.

• POST /api/observations: event_id (1–100 characters), site_id (1–150; must exist), mode (demo default or field), timezone-aware observed_at, success (boolean), seconds (finite, >0 and <=3600), carrier (up to 80, default Unspecified), note (up to 1000). Field writes require X-Sentinel-Token. An event ID is idempotent only when its contents match; conflicting reuse is rejected.

• POST /api/incidents/{id}/acknowledge: actor (2–100 characters), note (3–1000); whitespace-only values rejected. Field incidents require the token. Resolved incidents cannot be acknowledged. Saves actor label and action, but the shared-token pilot does not authenticate individual officer identities.

• POST /api/probe-upload: token required; accepts 1–262,144 bytes, discards the body, returns byte count and server time. No election records are expected or stored.

Observation and incident rules

Times are normalized to UTC. Observation time is when the test occurred; received time is when the server accepted the report. Future timestamps more than 60 seconds ahead are rejected. Reports older than 15 minutes or no newer than the latest report for the same site/mode are stored as history only. They do not alter current incidents.

Three consecutive failed observations spanning no more than 15 minutes open one incident per site/mode. Repeated failures do not create repeated open incidents. Two consecutive successes within 15 minutes resolve an active incident. Acknowledgment records ownership and action; it does not imply recovery. These thresholds are demonstration rules, not an INEC standard or statistically validated reliability model.

The delivery worker adds one escalation for a field incident remaining open and unacknowledged after 15 minutes. It uses the same configured recipients; regional recipient routing is not implemented. Missing check-ins are displayed as stale when viewing a site, but do not currently generate automatic outage incidents.

Outbox states

• pending: recorded, not submitted to a provider.

• sending: claimed by a worker before network submission.

• provider_accepted: SMTP or SMS provider accepted the request. Does not establish handset delivery, reading or acknowledgment.

• review_required: submission raised an error. A timeout may have happened after provider acceptance. Check the provider before retrying.

Demo entries remain previews regardless of the send setting. Workers claim field entries transactionally so concurrent workers cannot submit the same pending row. A crash after claim leaves sending; operators must reconcile it against provider records. There is no automatic retry of ambiguous sends and no delivery-receipt webhook yet. Provider credentials and recipients never appear in the public API.

Environment variables

.env.example is a reference, not automatically loaded. Configure the server, probe and delivery-worker environments separately.

• SENTINEL_DB: database path; default project data/monitoring.sqlite3.

• SENTINEL_INGEST_TOKEN: operator/probe shared secret. Unset rejects field writes and upload tests.

• SENTINEL_SEND: only literal 1 enables external sends; default disabled.

• SMTP_HOST, SMTP_PORT (587 default), SMTP_FROM, SMTP_USER, SMTP_PASSWORD, SENTINEL_EMAIL_TO: SMTP with STARTTLS and login. One configured email destination.

• TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_FROM, SENTINEL_SMS_TO: Twilio Messages API adapter. One configured SMS destination; sender and destination must be permitted by the provider account and destination-country rules.

Data identity and interpretation

Facility site_id is source name plus the GeoPackage feature identifier. source_identifier preserves the original registry/OSM identifier, which may repeat. IDs are reliable within these extracts; a new source release can renumber records, so reconcile identity before replacing a register that has monitoring history.

Potential duplicates use exact normalized names within approximately 200 metres between HOT health and GRID3. All records remain; the matcher does not prove distinctness when it finds no candidate. There are 914 candidates in the current build. No cross-source unique-facility total is claimed.

Source attribute values, including functionality and quality flags, are retained as supplied. Non-empty geometry is a technical acceptance criterion, not verification of positional accuracy. The 6,004 excluded GRID3 records require a separate coordinate-quality audit before any recovery.

External integrations

SMTP and Twilio adapters are implemented. Real delivery has not been tested with provider credentials. OpenCellID, VIIRS, RIPE Atlas, ODK, DHIS2, operator telemetry and INEC interfaces are not connected. The supplied OpenCellID token is not embedded. No automatic remote baseline download or national live coverage is claimed.
